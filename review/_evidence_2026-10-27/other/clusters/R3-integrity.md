# R3-integrity — new findings from the second pass (not yet independently verified)

## NEW-1-block-height-unbound-replay (found by verifier group 'completeness-critic-pass2') — Block.Height is attacker-chosen and never tied to the consensus height, so one Byzantine proposer (<1/3) replays old payments / updates / slash-evidence into a current block
- severity/confidence claimed: high/high
- locations: ledger/block.go:176-240 (ApplyBlock uses block.Height for every BlockID/evidence-window check, never compares it to the decided height), ledger/ledger.go:116-128 (LedgerState.Digest omits height — two different consensus heights with the same accounts/params/sequence share a StateDigest), node/node.go:494-517 (onProposal checks ProposalMsg.Height==n.height but never p.Block.Height), node/node.go:627-635 (commit re-applies the stored block with no block.Height==height check), findings.md:356-365 (deferred #7: claims the node layer guards this and it is 'not currently exploitable')
- attacker: A single Byzantine validator (holds one validator key, must be the scheduled proposer for some round — frequent and within the documented 'single dishonest/compromised validator' threat, below 1/3 power).

**Description.** The replay guard for payments and account-updates is BlockID==block.Height, and the evidence-age window is height-block.Height; all of these use block.Height, a field of the unsigned block body. Nothing — not onProposal, not the driver (it works on digests), not ApplyBlock — ever checks that block.Height equals the height being decided. LedgerState.Digest does not fold in height, so a block built on the current committed state but labelled with an OLD height has a fresh, valid StateDigest and a matching PrevStateDigest. A validator that is the scheduled round-0 proposer (1 of N; in a 4-set that is 25% < the 1/3 BFT bound and recurs constantly) proposes such a block; all honest nodes validate it (signature over the ProposalMsg.Height is correct, ApplyBlock passes because every guard reads the attacker's block.Height), prevote, precommit and commit it. findings.md deferred this (#7) as 'not currently exploitable (the node enforces monotonic height)', but the node enforces monotonicity only on its own n.height counter — it never binds block.Height — so the dismissal is wrong.

**Failure scenario.** 3 honest validators + 1 Byzantine validator key (below 1/3). Honest payment alice->mallory 30 commits at height 1 (alice: 100->70). At a later height H where the Byzantine key is the round-0 proposer, it re-proposes a block built on the current state but with Block.Height=1 carrying the SAME signed payment (BlockID 1). All 3 honest nodes commit it; alice is debited another 30 (70->40). Variants (ledger PoC): re-including a payment whose amount now exceeds the balance trips the overdraw ban and DESTROYS the victim's whole remaining balance and removes the account+name; an old reversed AccountUpdate (re-delegation / name / peer-DNS address) is re-applied; 4997-block-old slash evidence is re-applied by labelling the block height 3, confiscating a recreated account. Breaks security.md's 'a payment applies at most once' and the #5 evidence-age window.

**PoC.** .../scratchpad/verify-critic/node/poc_critic_height_test.go::TestPoCCriticByzantineProposerReplaysOldPaymentViaBlockHeight -> FAIL through the real 3-honest-node consensus path (alice 70->40, all nodes agree). Four ledger-level variants in .../scratchpad/verify-critic/ledger/poc_critic_height_test.go (ReplayTripsOverdrawBan, FuturePaymentAppliesTwice, StaleEvidenceWindowBypass, OldAccountUpdateReplay) all FAIL.

**Suggested fix.** Bind the height into committed state: add Height to LedgerState and its Digest, and have ApplyBlock require block.Height == previousState.Height+1. That closes this, the two certificate-replay findings, and the evidence-window bypass in one move (findings.md already names this as the deferred fix). Interim node-only guard: in onProposal and commit reject any block whose Block.Height != n.height.

## NEW-2-catchup-skips-dropoverdrawn (found by verifier group 'completeness-critic-pass2') — catchUp()/fastForward() do not re-run mempool.dropOverdrawn, so a node that self-recovers then proposes an overdrawing block that bans and destroys an honest payer's balance
- severity/confidence claimed: medium/high
- locations: node/node.go:341-352 (fastForward changes balances but never prunes the mempool), node/node.go:357-369 (catchUp -> fastForward -> startHeight, no dropOverdrawn), node/node.go:655-662 (commit DOES call dropOverdrawn, with a comment explaining exactly why skipping it bans the payer)
- attacker: None required (ordinary catch-up + payments split across reference nodes). An attacker could arrange the timing to grief a specific payer.

**Description.** commit() re-establishes the intake invariant after every block via mem.dropOverdrawn, because (its own comment) 'a pending overdraw left in the pool would make this node propose a block that bans — and destroys — the payer'. catchUp()/fastForward() change the committed balances the same way (adopting a peer's later state that may have debited a payer via payments admitted on other nodes, a reassignment, or a slash) but never run dropOverdrawn. A node that falls behind, self-recovers via the ordinary catch-up path, and is then the proposer will propose its still-pending payment set against the reduced balance; the ledger's overdraw ban fires on the honest payer, destroying its remaining balance and removing its account (and name). Every honest peer validates and commits that block.

**Failure scenario.** Payer holds 100; node A admits payer->shop 60 (block 3) while payer has 100. Meanwhile the network commits height 2 carrying the payer's other 60-unit payment (handed to a different reference node); payer now holds 40. Node A catches up to height 3 via a verified checkpoint (the normal catchUpLoop path) WITHOUT pruning, is the height-3 proposer, and proposes the now-overdrawing 60; the payer is banned and its 40 destroyed — by an all-honest network. PoC confirms the proposed block is valid for every peer and leaves the payer at 0 / removed.

**PoC.** .../scratchpad/verify-critic/node/poc_critic_catchup_overdraw_test.go::TestPoCCriticCatchUpSkipsDropOverdrawn -> FAIL (after catchUp the node proposes X1; ApplyBlock valid==true, payer balance 0, account removed).

**Suggested fix.** Call mem.dropOverdrawn (and updates/governance pruning as commit does) inside fastForward/catchUp after the new balances are set, before startHeight builds the candidate.
