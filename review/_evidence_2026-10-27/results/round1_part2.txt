
######## ledger-transition (ledger/*.go state transition: ProcessPaym
SUMMARY: The arithmetic and conservation core is sound for well-formed input, and propose/apply symmetry holds for accepted blocks: both paths run the same payments → updates → slashes → reassignment pipeline under the pre-block parameters, and ApplyBlock rejects wherever ProposeBlock filters. The digest covers every Account field, every parameter and the governance sequence. The governance-sequence replay fixes hold. The weak points are at the boundaries. (1) Nothing bounds a block, so fee-free updates can make every proposal undeliverable and halt the chain (PoC). (2) Amounts are decoded and size-checked too late: exponent-form big.Rat fields cost about 1.5 MB each at decode, and balances can grow without bound past the per-message cap. (3) Identity is a string, not a key, and a name is tied to the balance lifecycle: base64 aliases, and names released at zero balance and claimable in the same block. (4) Relative to the owner's 'two different signings means the key is burned' principle, a slash removes only the offender's own account. Delegated stake keeps the key in the dynamic set, the static set is untouched, and nothing tombstones the key. The overdraw ban, meanwhile, fires on a single over-balance payment, which the documented wallet closure does not cover. Each finding is backed by a failing PoC in the scratch copy except TOPO-1 (low confidence, script-only evidence).

NOTES:
Status of the 'two different signings means the key is burned' principle in this ledger:

| Signing | Detected as a burn signal? | What actually happens |
|---|---|---|
| Two conflicting consensus votes, same Validator string, same h/r/type | Yes (Evidence) | Only the offender's own account is removed. Delegations keep it in the dynamic set, the static set is unchanged, and the key can be re-funded (SLASH-1). |
| The same key under two spellings | No | Conflicting votes evade detection (KEYALIAS-1). |
| Conflicting proposals, conflicting governance votes for one sequence, receipts | No | Never turned into evidence (outside the ledger area; flag for the consensus and governance reviewers). |
| Payments | Overdraw ban is the only analog | Fires on a single over-balance payment (OVERDRAW-1) and is undone by any same-block credit (OVERDRAW-2). |

Caveats:
- RAT-DECODE-1's 1 MiB figure is extrapolated linearly from a 40-field decode (59 MB). I deliberately did not run the full body on the shared machine.
- RAT-GROWTH-1's timings were taken on a shared, loaded machine. That test takes about 90 s; BLOCK-SIZE-1 takes about 100 s with GOLEDGER_CHAOS_SLACK=4.
- Minor hygiene (not reported as a finding): evidenceInWindow computes height - e.A.Height without overflow care, so votes signed at heights near MinInt64 stay 'in window' forever. Only the offender's own key can produce them, which is harmless and consistent with burning.

######## governance
SUMMARY: The ⅔ certificate machinery (sequence single-use guard, quorum math, duplicate/unknown-voter rejection, non-negative guard, at-most-one-action-per-block, full-profile digest coverage) is sound WITHIN a single live chain. The weaknesses are at the seams. Two break supply/liveness invariants the docs advertise as guaranteed: a reassignment is validated against the pre-block balance but applied as an ABSOLUTE set AFTER payments, so an account's same-block outflow is minted a second time (unratified inflation, invisible per-account); and LedgerParameters.Acceptable has only lower timing bounds, so a ⅔ vote can set a block interval of centuries and halt the chain irreversibly. Two more are unauthenticated-reach problems into the governance pools (permanent freeze by slot-squatting; a ~500-byte packet stalling the event loop ~9s via big.Rat exponent amplification). The eMudhra "burned key" principle does not hold here: in no validator mode does slashing durably remove a proven double-signer's voting/governance power. Plus a pooled-vote poisoning liveness wedge and a cross-re-genesis certificate/payment replay. All seven are traced end-to-end with failing PoCs.

######## NODE TRUST ANCHORS — onboarding, catch-up, snapshot and back
SUMMARY: The adoption plumbing is mostly solid: all three paths (adopt, catchUp, loadSnapshot) gate on a real >2/3 Commit.Verify, bind the commit to the full LedgerState digest (accounts+params+governance sequence), enforce strict height monotonicity (never roll back), reject other-network snapshots via network-bound vote signatures, and the going-forward validator set is re-derived from verified state. The same genesis-anchoring, flipped, permanently bricks onboarding/recovery once the set rotates fully past the founders (SYNC-3). Separately, the catch-up client reads a peer's checkpoint with no size bound (SYNC-2).
