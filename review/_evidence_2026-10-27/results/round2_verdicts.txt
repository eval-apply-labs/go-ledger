
######## burn-slash

--- C01-slash-not-burn => CONFIRMED / medium
REASONING: All 5 reports share one root cause: applySlashes deletes one account and nothing records the key. I rebuilt it through the real pipeline: a byzantine agent double-signs, honest drivers record the evidence, a proposed block carries it, and ApplyBlock slashes on every node.
- STATIC: the key stays in the set. Its later precommits count in commit certificates, honest proposers re-carry the evidence in every block (8/8), and after the slash it cast the deciding ⅔ vote for a 1000-unit reassignment that enacted.
- DYNAMIC/DELEGATED: it keeps 200 of 800 power and co-signs commits.
- DYNAMIC/SELF-STAKED: it is ejected, then re-admitted by one 60-unit sock-puppet payment. commit() had already pruned the evidence, so 0/18 later proposals re-slash it.
Downgraded from high: under <1/3 Byzantine there is no fork or mint. The harms are accountability, ⅔-governance weight, and a permanent fault-budget loss: with 5 equal validators, one sleeping laptop plus the abstaining slashed key stalls the chain, while excluding the key (quorum 3) keeps it live. SLASH-1's '≥1/3 key → unrecoverable stall' is outside the model, and no burn fixes it, because the evidence block needs the quorum the attacker withholds. DOCS-1 confirmed (README:77, consensus.md:79, managing-the-currency.md:40).
PRECOND: A validator key that double-signs. That means a compromised key, an operator running one key on two machines (failover, or the planned separate-signer setup), or today an honest validator that reboots mid-height (H1). Static mode is the documented default; delegation is the owner's bank model.
FIX: A committed burn set behind one choke point:
(1) LedgerState.Burned: sorted canonical keys, hashed into Digest only when non-empty. Existing digests and snapshots stay valid, so this is a coordinated binary upgrade with no re-genesis. Checkpoint and Snapshot carry it.
(2) applySlashes adds each offender. Evidence is admissible only if the offender is in the pre-block validator set, not yet burned, and appears once per block. This stops a byzantine proposer bloating the set.
(3) validatorsForState(accounts, burned): static = config minus burned; dynamic = deriveValidators skipping any ValidatorNode in the burned set. Every consumer already checks set membership, so the burned key's votes, proposals, commit signatures, checkpoint vouching and ⅔ governance votes are all refused with no further code.
(4) Node: prune pendingSlashes only once the key is burned or the evidence ages out, not when the key leaves the set.
PITFALLS: - Must not ship before H1's fix. On the prototype an ordinary reboot burned an honest validator: the 4-equal static set became 3 with quorum 3, i.e. zero fault tolerance. Wrongful honest burns also raise the Byzantine share of the shrunken set (1 Byzantine of 4, after 1 honest burn, is 1/3).
- Needs C18's canonical-key rule, or an alias spelling bypasses the burn.
- Every LedgerState construction must carry Burned. Missing it in startHeight's ProposeBlock stalled my first prototype right after the first burn; TestChaosEquivocatorIsSlashedWithoutFork caught it.
- A burn is irreversible in-protocol. Add a ⅔ un-burn/re-admit governance action or document re-genesis.
- Residual: an offender that leaves the set before its evidence lands and stays out past the 1000-block window escapes.
- Skip round-1's 'reset delegations' and 'refuse re-funding' suggestions: they mutate state or intake with n
INTERACTIONS: - H1 is a prerequisite.
- C18 provides the canonical keys the burn set needs.
- C28: harvest-before-replace is included in the prototype.
- C02/naming decision: a slash must not delete a named account.
- C11: a burned voter's pooled vote now poisons Valid(), so burned voters must be pruned from governance pools.
- C03: under the owner's principle, proposal equivocation should feed the same burn set.
- C19: checkpoint anchors must use the anchor state's burned set.

--- C18-base64-key-aliases => CONFIRMED / low
REASONING: Reproduced through production intake. POST /hdls/update with Delegated set to an alias spelling of V returns 202 and commits. deriveValidators then yields V and V' as two 100-power identities for one key. V precommits X and V' precommits Y at the same (h,r): both are counted, no evidence is recorded, and hand-built Evidence is invalid.
Go's StdEncoding accepts 3 non-canonical trailing-bit spellings, which Strict() rejects, plus any \r/\n insertion, which Strict() also accepts. So Strict() alone is not enough.
Downgraded to low:
- Dynamic mode only.
- The attacker gains nothing over splitting the same stake across two real keys: no extra power, the same <1/3 bound, and the same slash evasion.
- In static mode it can only arise from operator error.
Its real weight is as a constraint on C01: a tombstone keyed by the base64 string is bypassed by a seat or stake held under an alias, so the burned key keeps voting. It would be medium if a string-keyed burn shipped without the canonical rule.
PRECOND: Dynamic validator mode. The key holder (necessarily byzantine) controls at least threshold stake and places it under an alias via AccountUpdate.Delegated or a payment to the alias. No honest client ever produces aliases.
FIX: Canonical-key rule: a key string is valid iff it decodes with StdEncoding and base64.StdEncoding.EncodeToString(decoded) == s; the scheme checks the length.
(1) Enforce it in signing.VerifyBase64. This is one line and makes every signing identity canonical-only: votes, proposals, payment From, update From, governance votes and evidence. Prototyped; it breaks no test.
(2) Apply the same predicate to the non-signing key fields that create identities: Payment.PublicKeyTo, AccountUpdate.Delegated, Reassignment.Account, and genesis/static config. Check them at intake, in ProposeBlock/ApplyBlock, and at config load, so no unsignable alias seat or stranded alias account can exist.
The burn set is then keyed by the canonical string with exact-match lookups. No digest or signing-preimage change, no re-genesis.
PITFALLS: - Strict() misses the newline aliases.
- Doing only (1) leaves alias seats that can never vote: dead weight in the quorum denominator, plus alias-keyed funds that wallets keyed by the canonical string never see.
- (2) is a consensus rule needing a coordinated upgrade. Several tests use non-key account strings ('bob', 'D1') and would need real keys.
- Don't canonicalize on lookup at every comparison site; that is fragile. Reject non-canonical keys at the edges instead.
INTERACTIONS: Required by the C01 burn design. C26: config-load key validation is the natural home for the static-set check.

--- C28-evidence-dropped-on-catchup => CONFIRMED / low
REASONING: The round-1 PoC is valid: it drives the same handlers the event loop runs (two evVote events, then catchUp with a real ⅔ checkpoint), and the driver's evidence is discarded without being harvested.
I also reproduced a broader and more common variant through the live loop. A validator sends its conflicting precommit after the height decides. 38 valid double-signs reached every honest node and none was ever slashed. Such votes either:
- reach the decided driver during the post-commit window, which startHeight then replaces without harvesting; or
- reach the next height's driver, which drops them on height mismatch.
The round-1 fix (harvest in fastForward/catchUp) covers neither path. Low: a late double-sign cannot affect a decided height, and an equivocation that actually splits votes usually has both halves relayed to nodes before they decide. The gap only lets a double-signer dodge the burn principle by timing.
PRECOND: A validator that double-signs late, or a node that witnessed an equivocation and then resolved the height by checkpoint catch-up.
FIX: (1) Harvest driver.Evidence() into pendingSlashes at the top of startHeight, before any driver replacement. This covers both the post-commit window and the catchUp→startHeight path; today harvesting happens only in commit().
(2) In the evVote handler: if a precommit is for (lastCommit.Height, lastCommit.Round) and lastCommit.Votes holds a different-digest precommit by the same validator, record Evidence{A: held, B: v}.
Both are node-local, about 15 lines, with no digest or preimage change. Prevotes from past heights stay uncovered because they are not retained.
PITFALLS: Land after H1's fix. An honest validator that reboots mid-height emits exactly these late conflicting votes; today this gap is what spares it, and (2) would slash or burn it. Harvested evidence must still pass the burn admissibility check (offender in the current set).
INTERACTIONS: H1 must land first. C01 (evidence lifecycle; (1) is in the prototype). C21 (the same post-commit window).

--- H1-crash-restart-self-equivocation => CONFIRMED / high
REASONING: Confirmed. No own-vote or sign state is persisted, so after New(sameConfig) loads the H-1 snapshot, startHeight builds a fresh round-0 driver.
The deterministic trigger is the proposer case: the restarted round-0 proposer rebuilds its candidate from an empty mempool, re-proposes a different block and prevotes it inside Driver.Start, before any network input. Peers still hold its first (H,0) prevote, so valid Evidence exists; the restarted node also records evidence against itself.
Consequences through the real stack:
(a) Restarted validator with 2/4 power: permanent halt in 2/2 runs. Either the network sticks at round 0, or it live-locks: peers stay locked on the original block whose proof-of-lock no longer reaches quorum, because the restarter's prevote is un-counted.
(b) The docs' laptop shape, 4 equal validators with one asleep: when the sleeper wakes, the honest X loses its whole balance in 9/12 runs, and 3/12 runs deadlock permanently with all four online (whenever the stall had reached round 1). On the burn prototype, X is burned and the set shrinks from 4 to 3.
(c) With ≥1/3 power plus a Wi-Fi drop: a fork (see VBS-N2).
Non-proposer restarts: 0/6 trials equivocated. TODO.md's 'not a safety issue' is wrong.
PRECOND: (1) The restarted validator is the round-0 proposer of the open height; the chance is proportional to its power.
(2) Its pre-crash block was non-empty: any queued payment, update, governance certificate or evidence. An empty block is re-proposed identically.
(3) The height is still open when it returns. This is automatic if its power is needed for quorum (a ≥1/3 machine under 'concentrate stake', or one other laptop asleep), because its own crash then stalls the height.
(4) It dies between its f
FIX: Persist before signing, then restore on restart:
(1) Before broadcasting any own proposal or vote, append it to a per-height file and fsync it: the own proposal (digest and block) and own signed votes. That is at most 3 records per round, and the file is truncated at commit.
(2) On startHeight at that same height after a restart, rebuild the driver from the file: sentPrevote/sentPrecommit per round, the own proposal per round (re-propose that block, never a new candidate), and lock/valid state from own non-nil precommits. Re-broadcast the logged messages.
(3) As defense in depth, and as the contract for the planned remote signer: refuse to sign a different message for an already-signed (H, R, type).
(4) Fix castVote's sign-error path (VBS-N1).
All of this is node-local: no digest or preimage change, no re-genesis. The cost is one fsync per own vote.
PITFALLS: - The lead's refuse-only high-water-mark guard stops the slash and the fork but not the halt. As proposer, startRound sets proposals[0] to the new candidate, signing is refused, and castVote returns nil while step1 reports progress, so evaluate() spins forever (reproduced; VBS-N1). Because the guard persists, every restart re-hangs. Even with the spin fixed, the driver never learns its first prevote, and proposers arm no propose timer, so it never precommits.
- 'Resume at persisted round+1' fails in the 4-equal case: a 1/4-power node's next-round votes are below the f+1 skip threshold, so peers stuck at round r never follow.
- Using the network as the WAL (adopting own votes from peers' re-gossip) misses the fork, because the peer holding the lock-bearing precommit has already moved on.
INTERACTIONS: - H1 is a prerequisite for the C01 burn; otherwise ordinary reboots permanently burn honest validators (shown on the prototype).
- It is also a prerequisite for the C28 fix, which would start slashing rebooted validators.
- The planned separate signer must keep the sign log, and the node must still restore its driver state.
- VBS-N1 must be fixed alongside.
- C21's post-commit window currently spares some restarts.

NOTES: Fix order: VBS-N1 → H1 (with the lock restore) → C18 canonical keys → C01 burn set → C28 late harvest. Landing the burn or C28 before H1 turns ordinary reboots into permanent burns of honest validators; this was shown on the prototype, where the honest X was burned and the 4-equal set shrank to 3. The burn prototype (+117/-36 lines, 8 files: <scratch>/burnset-prototype.patch, tree at <scratch>/verify-burn-slash-fix) closes all three C01 modes and passes every existing suite. TestChaosDynamicAdmissionConverges is a pre-existing flake (fails 1/6 on both the pristine and prototype copies). The H1-B deadlock outcome also occurs on unmodified code, so it is not a prototype artifact. The harness is an in-memory bus with a precise crash point; HTTP is used only for the sleeper's bootstrap. All my PoCs are in <scratch>/verify-burn-slash (zz_vbs_*); the pristine checkout is untouched (git status is clean). Not tested: the non-proposer H1 path with a governed StepTimeoutMs below cfg.Timeout.

######## proposals-liveness

--- C03-proposal-equivocation => CONFIRMED / medium
REASONING: Real, through the production intake. onProposal's held fast path (node.go:498) only drops a SAME-digest copy. A second, different-digest proposal signed by the scheduled proposer passes the proposer and signature gate. It is ApplyBlock'd, stored in n.blocks and relayed (relay dedup is keyed on h:r:digest). The driver keeps the first proposal, and Evidence() scans only vote sets, so nothing is ever recorded. The same holds in static and dynamic mode and on HTTP and gossip intake; no other guard exists. The round split alone is not new damage: a Byzantine proposer can always waste its own round by staying silent. CometBFT does not slash this either, but it never relays a second proposal. What is real: (1) it breaks the owner's burn principle; (2) the 'relay and re-apply every distinct signed proposal' path is unbounded. It is not 2x but K x, and works for any round (see new finding NF1, high). Also, nodes that hold the losing block cannot decide the winning one and must wait for checkpoint catch-up. Taken alone, the accountability gap is low. Medium reflects the shared root cause.

--- C12-reassignment-outflow-mint => CONFIRMED / high

--- C15-block-size-unbounded => CONFIRMED / high
REASONING: No guard stops it, and the attack is cheaper than round 1 reported. ProposeBlock carries every valid payment and update naming the height; ApplyBlock has no count or byte bound; every peer decodes /hdls/proposal under MaxBytesReader(1 MiB) (httptransport.go:308). Updates need neither a fee nor an account: ProposeBlock and ApplyBlock check only BlockID, signature and size, applyAccountUpdates silently skips an unknown From, and evUpdate admits any BlockID. The pool caps do not bound it: the update pool cap is MaxMempool (default 10000 per node, shared across all heights), and about 545 updates of 1.9 KB (about 5% of the cap) are enough. MaxMessageBytes bounds a message, not a block. The candidate is built once per height from the gossiped pool, and pools are pruned only on commit, so every proposer in every round holds the same oversized block: a permanent halt. The only recovery is manual: a restarted node has an empty in-memory pool and can commit a small block when it is proposer, but the attacker re-posts. Static and dynamic modes are identical.

--- C06-single-overdraw-ban => CONFIRMED / medium

--- C22-wallet-dns-rebinding => CONFIRMED / high
REASONING: sameOrigin() (ui/main.go:76-86) rejects only Sec-Fetch-Site cross/same-site and, when Origin is present, requires Origin.Host==r.Host. It never compares against the fixed -listen authority (grep confirms the only Host use is u.Host==r.Host). After a DNS rebind the browser's page-origin and request-URL share the attacker's name, so Origin.Host==r.Host holds by construction and the request is treated as the local operator's. The wallet auto-signs with the local key, so a drive-by page drives real signed payments and governance votes. Header realism: the browser sends Host=<attacker name>:<port> (never the resolved IP) and Origin=http://<attacker name>:<port>; whether it also sends Sec-Fetch-Site:same-origin (trusted branch) or omits it (Origin==Host branch) the guard passes either way, so the bypass does not depend on the Sec-Fetch nuance. No node-layer guard helps: the payment is validly payer-signed, so VerifyPayment/admitPayment accept and commit it. The blanket no-header 'curl' return true is a second independent bypass for any non-browser client that reaches the port.
PRECOND: Victim runs the wallet (default 127.0.0.1:8090) and, while it runs, visits an attacker web page that rebinds its hostname to loopback (Singularity-style, TTL 0). Fits docs/security.md (single dishonest party; low-to-moderate value). Payment drain is unconditional. The reassignment MINT needs ⅔ to enact, so it is instant only on a sole-validator/demo wallet or where the victim holds >=⅓; on a larger set the vote merely pools, but the payment still moves money.
FIX: In the guard, reject any request whose Host header is not the configured -listen authority (a small fixed allowlist, e.g. 127.0.0.1:<port> and localhost:<port>), independently of Origin, and additionally require Origin/Referer, when present, to equal that same value; keep binding to 127.0.0.1. This defeats rebinding because the browser always sends the navigated name as Host, never the loopback IP, so the attacker name never matches the allowlist. Drop the blanket no-header 'return true' or gate it behind a loopback-peer check. Add X-Frame-Options/CSP frame-ancestors 'none' as defense-in-depth. Wallet-only change; no digest/signing-preimage impact, no re-genesis.
PITFALLS: The allowlist must be derived from the actual -listen value (a 0.0.0.0 or :8090 listen needs the operator-reachable host(s) added, or legitimate access breaks). Keep allowing an empty Host only for genuinely local non-browser tools if the curl escape hatch is retained, and gate it on a loopback RemoteAddr. Existing security_test.go cases still pass (same-origin to 127.0.0.1:8090 is allowed; cross/same-site still blocked).
INTERACTIONS: The governance impact is bounded/amplified by the governance clusters: a rebound reassignment vote is only as dangerous as C12 (post-payment absolute-set mint) and C25 (name resolution via untrusted node) allow, and needs ⅔ to enact except in sole-validator/demo mode. The owner's burn rule does not help: attacker-driven payments/votes are individually valid, not equivocation, so nothing slashes them.

--- C26-keypair-consistency => CONFIRMED / medium
REASONING: Two independent instances of the same root cause: trusting a stored/configured public key over the private key, with no derive-and-check. (A) cmd/server load() (config.go:78-83) validates only key LENGTHS (the C4 fix), never that ed25519.PrivateKey(priv).Public()==pub. Go's ed25519.Sign binds priv[32:] into every signature, so a config pasting pub from one keygen and priv from another (both correct length) loads cleanly but every vote/proposal/receipt verifies under priv's real pub, not the configured identity it is listed under. castVote swallows signing errors but here signing succeeds and verification-under-the-wrong-identity is what fails, and nothing self-tests it: a silent consensus ghost — the exact C4 failure mode reachable past the length-only check; a >=⅓-power ghost is a liveness stall. (B) ui/keyfile.go:74-84/141 decodes the stored publicKey as the wallet identity without deriving it from priv, and sealPrivateKey uses gcm.Seal(...,nil) (empty AAD) so KDF params/iterations/salt/version and the plaintext publicKey are unauthenticated — a tampered/corrupted publicKey yields a substituted receive-address identity with no error.
PRECOND: (A) Operator assembles node.json from two keygen outputs or rotates one field — no attacker; docs/security.md names operator misconfiguration/'bugs with no attacker' as a primary threat. (B) Victim restores a tampered-but-sealed backup (manual calls a sealed backup 'safe to store anywhere'), or a disk bit-flip in the unauthenticated publicKey field — low severity because outbound payments then fail node verification loudly, bounding stealth to misdirected INBOUND payments.
FIX: (A) In load(), after decoding, require ed25519.PrivateKey(priv).Public() equal the configured pub, and/or add a one-shot sign+verify self-test in node.New/Start that fails fast — this completes the C4 fix. (B) Derive the wallet identity from the decrypted private key (priv[32:]) and ignore or equality-check the stored publicKey; optionally bind version+KDF params+pub into the GCM AAD. Both are small, local, no digest/signing-preimage change, no re-genesis.
PITFALLS: (A) The derive-and-check assumes a well-formed 64-byte key (comparing to priv[32:]); harmless for any keygen output. (B) The derive-pub-from-priv half is fully backward compatible; the GCM-AAD binding is NOT — already-sealed wallets were sealed with empty AAD, so open() with non-empty AAD would fail to unlock them (needs a read-old/re-seal migration). Prefer shipping the derive-and-ignore-stored-pub half first (higher value, zero migration).
INTERACTIONS: (A) extends C4 (findings.md GLM review, recorded FIXED) — same lineage, the self-test is its completion. Both halves share the theme with C22/C23 that the key does harm or is mis-bound without an obvious leak. A ghost validator holding >=⅓ turns this into the liveness stall the owner's governance-liveness concern depends on.

--- C36-no-key-rotation => CONFIRMED / medium
