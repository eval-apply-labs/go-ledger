
######## NODE UNTRUSTED-INPUT BOUNDARY (node/httptransport.go, node/n
SUMMARY: The intake boundary is mostly disciplined: payments and account-updates are signature-verified before admission/relay, checkpoints are quorum-verified off-loop before touching the event loop, far-future heights/rounds are dropped (onProposal height gate, ReceiveVote maxRoundLookahead), proposals are proposer-authenticated, and the mempool/update pools are size-bounded and content-deduped. But three cheap, unauthenticated amplification/state-growth vectors earlier rounds missed survive, all reachable by anyone who can reach the port (the documented trust boundary): (1) a ~60-byte payment whose Amount is an exponent literal like "1e1000000" expands to a 3.3M-bit rational and burns ~100-150ms of single-event-loop time per request via big.Rat RatString/Marshal — slipping entirely under the 1 MiB body bound that security.md claims prevents JSON DoS; (2) consensus votes are relayed and stored in heightVotes before any signature/validator check, so junk is amplified to every peer and grows an uncapped map; (3) governance vote pools create a slot before verifying any vote, letting 64 vote-less junk proposals permanently brick parameter/reassignment voting. The /hdls/resolve answer is anchored to a committed digest but not provably bound to it, and the documented "compare digests across nodes" cross-check is weaker than claimed. All four are code-fixable and extend deferred #10 with concrete new angles. No mint/steal/fork vector was found at this boundary.

######## WALLET + ADMIN UI (ui/ module: main.go, wallet.go, keyfile.g
SUMMARY: The wallet is well-structured and several prior findings are genuinely fixed (html/template is used so on-chain strings auto-escape; receipt verification checks signature+PaymentID+validator-membership; the CSRF guard blocks ordinary cross-site/same-site browser POSTs; the hand-rolled PBKDF2-HMAC-SHA256 matches the stdlib on 300 randomized vectors incl. >block-size passwords and multi-block output). But the localhost-only, auto-signing design leans entirely on the origin guard and on key-at-rest sealing, and both have gaps. The headline is a DNS-rebinding bypass of the CSRF guard (KEY-1, high): the guard compares Origin.Host==r.Host rather than a fixed expected host, so after a rebind a web page the user merely visits can drive signed payments and governance votes with the local key — exactly the "key does harm without being leaked" shape the owner is worried about. On the key-at-rest side, following the tool's own documented remediation (set GOLEDGER_WALLET_PASSPHRASE) silently does NOT seal an already-created plaintext wallet (KEY-2, medium), and the public key in the file is unauthenticated and trusted over the private key (KEY-5, low). Two more: the persisted payment-block counter is poisoned permanently by one bad/malicious height report or a documented re-genesis (KEY-3, medium), and reassignment (mint) votes still resolve the typed name to a key via the untrusted node, so a validator signs a certificate targeting a key they never saw (KEY-4, medium) — the same class that was fixed for the payment path but left in the mint path. All five are traced end-to-end with failing PoC tests.

######## flake-suite — TestPaymentGossipReceiptAndReplay root-cause +
SUMMARY: TestPaymentGossipReceiptAndReplay is NOT a test-timing artifact. It reliably detects a real node liveness bug: a block proposal that arrives in the post-commit window — after commit(H) increments the height but before startHeight(H+1) builds the new driver (the MinBlockInterval gap) — is authenticated against the OLD height's proposer schedule, dropped, and never re-processed. The height's first proposal attempt is simply lost; recovery waits for the proposer's next reGossipProposal tick (every cfg.Timeout: 5s in the test, default 3s in production). When ≥2 of 4 nodes hit the window the whole height stalls ~one step-timeout, and the test fails when enough heights stall to blow the 20s deadline. A deterministic PoC (one hand-driven node, no reliance on scheduling) reproduces the drop with a >1s margin, and a throughput PoC shows an all-honest, zero-loss 4-validator LAN commits only ~25% of the blocks it should, spending ~2/3 of wall time stalled. A second, independent defect (timeouts are not height-scoped: a propose timer armed at height H fires into height H+1's driver and prevotes nil prematurely) adds variance and rejects timely proposals. A third, unauthenticated defect surfaced while tracing: the proposal signature does not cover the block body, and onProposal records/relays/re-gossips the first-seen authentic-signature copy even when its body fails ApplyBlock, then dedups every genuine copy — so one keyless swapped-body copy delivered first poisons a node's view of the round. A prototype fix (height-scoped timeouts + hold-and-replay the window proposal into the new driver) takes the same network to ~100% of ideal throughput and keeps the whole suite -race green. The full suite (no -short) ran twice under -race with GOLEDGER_CHAOS_SLACK=4 plus the ui module under -race: all green, no data races, no fork/supply violations.

  LOC: node/node.go:495, node/node.go:466, node/node.go:656, node/node.go:587, node/sync.go:67
  DESC: commit() does n.height++ then schedules startHeight(H+1) one MinBlockInterval later (node.go:656,678).
