CON-1 wrong: the safety argument in docs/consensus.md is misstated.
- docs/consensus.md:21-23 "the overlap holds an honest validator, who never precommits two blocks for one height"; :57-58 "The lock keeps a validator from precommitting two blocks across rounds". Same shortcut in consensus/errors.go:7-9 (package comment), consensus/consensus_test.go:228-230 ("at the same height"), README.md:134-139 (also says the lock "makes it live") and docs/security.md:41-42.
- Code: the lock rule (driver.go:433-442) locks on, and precommits, any proposal with > ⅔ prevotes in the current round, whatever the node is already locked on. prevoteFor (driver.go:474-485) releases the lock given a proof-of-lock from a round at or after the locked round (TestDriverPOLUnlockReleasesLock). commit.go:11-13 says correctly that the intersection argument is per round.
- Probe: an honest driver precommits X in round 0, then Y in round 1 after > ⅔ prevotes for Y (precommit round 0 block 11, precommit round 1 block 22).
- Fix L21-23: "Two sets that each hold more than ⅔ overlap in more than ⅓, so the overlap holds an honest validator, and in one round an honest validator never precommits two blocks (TestConflictingCommitsRequireEquivocation). Across rounds the lock carries it: once a block has > ⅔ precommits in a round, the honest ones among them, more than ⅓ of the power, are locked on it, so no other block gets > ⅔ prevotes in a later round."
- Fix L57-58: "The lock keeps a validator from prevoting another block in a later round unless it holds > ⅔ prevotes for that block from a round at or after its lock (TestDriverLockingPreventsConflictingPrevote; the release is TestDriverPOLUnlockReleasesLock). An honest validator can precommit two blocks at one height, in two rounds; that is no double-sign."
- README: say "in one round" and "the lock keeps it safe across rounds and the timeouts make it live".

CON-4 wrong code comment / liveness: a refused precommit of a locked value is never retried.
- castVote comment (driver.go:333-337): if signing or the sign log fails, "nothing changes ... the rule that cast the vote reports no progress and fires again on the next event". findings_20261027.md:240-241 (E31) says the same.
- The lock rule (driver.go:433-442) sets the lock and consumes gotPrevoteQuorum before castVote, and reports progress even when castVote returns nil.
- Probe: after a refused precommit of X, the lock is set and the next event casts no precommit; the prevote timeout then precommits nil while locked on X. Safe (nothing released) but a liveness loss on a full disk or a down signer.
- Preferred (code, about 3 lines): consume gotPrevoteQuorum and take the lock only when castVote returns actions (voted() already takes the lock), otherwise fall through. Fallback: say in castVote's comment that the lock rule is the exception.

Fix: "on disk from the next commit or catch-up", and "or the name's key changes (the ⅔ action, or a key change it files once unseated)".
